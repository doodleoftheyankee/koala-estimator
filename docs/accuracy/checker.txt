THE ACCURACY CHECKER (rebuilt in the baseline stage, Nov 19 2026)

What it checks
  Eight rules every quote must keep, written from the audit and the owner decisions (OD1-OD11):
  - items_add_up            the items printed under an option add up to its printed total (S1-F2)
  - same_work_same_price    the same work item in the same area has one price in every option (S1-F3, OD2)
  - options_step_up         the options shown do different work and each costs more than the one before (S1-F7, OD6)
  - labels_match_work       titles and bullets promise only priced work: "to Code", "Remove", "Air seal" (S1-F7);
                            "fills the cavity" only when it is full, and an item's R only when its quantity
                            reaches it (full_cavity_not_filled, qty_below_stated_r: R3, R6; cavity stage)
  - cavity_not_overfilled   what is installed fits the cavity with what is already there; a wall with no
                            depth is a 2x4, 3.5 in (S1-F4, S1-F5, S1-F6, OD5)
  - finite_amounts          no blank, infinite or negative amount (a price adjustment line may be negative)
  - same_price_text         every surface reads an option's price in whole dollars, and every list shows the
                            recommended option's price (S1-F1, OD1, OD4); surfaces in PRICE_SURFACES
  - valid_until_is_expiry   "Valid until" is the business-zone day the link stops working (S1-F8, OD11)
  Engine rules: lib/pricing/invariants.ts. Quote rules: lib/quotes/invariants.ts. Unit tests on hand-made
  good and bad quotes: lib/accuracy/invariants.test.ts.

How to run it
  npm run accuracy:violations -- 10000 20261118
      10,000 random quotes (lib/pricing/__fixtures__/random.ts) from seed 20261118, priced with the
      seeded setup; prints per rule the quotes that break it, the breaks and the breaks by kind.
      Takes about 70 s. Add --rows <rows.json> to price with other pricing rows.
  node scripts/accuracy/run.mjs scripts/accuracy/price-golden.ts synthetic <out.json>
      The 65 synthetic estimates (scripts/accuracy/golden-synthetic.json, written by make-synthetic.ts).
  node scripts/accuracy/run.mjs scripts/accuracy/price-golden.ts live <golden dir> <out.json> [<summary.json>] [--with-accuracy-rows]
      The live estimates. --with-accuracy-rows prices rows exported before the accuracy migration
      (20261119000001) as they read after it (lib/accuracy/rows.ts withAccuracyRows).
      The export is read-only and never committed:
        1. run scripts/accuracy/golden-export.sql and scripts/accuracy/bundle-rows.sql (as
           select rows::text as rows_text, md5(rows::text) as md5 from (...) x) on production, SELECT only;
        2. node scripts/accuracy/run.mjs scripts/accuracy/make-live-golden.ts <estimates result> <rows result> <golden dir>
           checks the copy against the database's md5 and counts and writes live-estimates.json and live-rows.json.

Keeping it true
  - shownOptions (lib/pricing/invariants.ts) is what the customer is shown. Give it the engine's default
    result: the engine returns only shown options (OD6) and names each one it hides in an option_hidden
    warning; an option so named, or marked hidden, is never counted. A showAll result is not what the
    customer sees (violations.ts prices with showAll only to count every option).
  - Items are read by their kind (itemKind; an item stored with no kind is work). Job-level lines
    (travel, minimum, adjustment) have no area and are not "work".
  - Existing insulation is read with the one R-per-inch table (lib/pricing/rPerInch.ts); a material
    not in it is read at the highest R per inch, as the engine does. A sized material (a batt) adds its
    rated R and is as thick as its row says.
  - The random generator keeps its own copy of the 2026-11-18 per-inch table, and draws everything but
    the estimator's changes from the seed in a fixed order, so the same seed draws the same areas,
    crews, drives, picks and dates whatever the app's table, the engine or the prices say (review A
    F7). The estimator's price and line changes come from each quote's own stream and start from the
    engine's numbers, so only their amounts follow the engine.
  - bundle-rows.sql and loadPricingBundle load the same materials: active, and the default, one for a
    job type (dense-pack walls) or a size (batts). The new columns are read through to_jsonb so the
    query also runs on a database without the accuracy migration.
  - PRICE_SURFACES lists each place a price is printed with its file, line and snippet; a test fails when
    a snippet leaves its file. When a surface changes, update its entry and priceTexts with it.
  - The quote rules read documents the app builds today (sampleQuote: format 2, a counter number, the
    consent for a sample state). A document sent before the quotes stage has no format and prints as
    it did (cents in its sentences, its printed Valid until), so checking a stored document would
    report those surfaces: that is hard rule 1 at work, not a new fault. The thank-you page is
    rendered for real (SignForm's SignedThanks).
  - Hard rule 1 (sent and signed quotes never change): scripts/accuracy/render-stored.ts renders the
    stored quotes (scripts/accuracy/quote-docs-export.sql, read-only, people replaced) in every state,
    with their PDFs and emails, through the real code; render it on two commits and diff the folders
    (docs/accuracy/after-quotes/hard-rule-1.txt).
  - After a migration that changes a seeded value: DATABASE_URL=... bash scripts/accuracy/seeded-rows.sh
    and commit lib/pricing/__fixtures__/seeded-rows.json with the migration. A new pricing setting key
    goes in PRICING_SETTING_KEYS (lib/accuracy/rows.ts) and in bundle-rows.sql.

Before any fix (docs/accuracy/before/)
  violations-20261118.txt, golden-synthetic-before.json (in full), golden-live-before.json (counts and
  option totals by estimate id only).

After each stage
  docs/accuracy/after-money/, docs/accuracy/after-cavity/ and docs/accuracy/after-quotes/: the random
  run and both golden sets after that stage (about.txt in each says how they were made);
  after-quotes/hard-rule-1.txt also says how the stored quotes were compared.

After Phase 1 (flow stage) and the before/after report
  docs/accuracy/after/: violations.txt (10,000 at seed 20261118, 20,000 at seeds 7 and 99999),
  golden-synthetic-after.json and golden-live-after.json.
  node scripts/accuracy/run.mjs scripts/accuracy/report.ts <golden dir> docs/accuracy/report/report.json docs/accuracy/after
      prices both golden sets, compares them with docs/accuracy/before/ and explains every
      difference (stage, ledger ids, owner decision); a difference it cannot explain is printed as
      UNEXPLAINED. <golden dir> is the read-only live export (with live-priced-before.json), kept
      out of git. report-summary.txt says the same in plain words.
